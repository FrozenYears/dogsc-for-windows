# 项目工作规范

本文件约束 dogsc-win 的开发协作方式。所有参与者（含 AI 助手）必须遵守。

## 1. 决策必须走 ask

任何**需要产品/资源判断**的选择，必须以提问形式向项目所有者提出，不得自行拍板或默认采用「技术最优」。

要求：

1. 一次性罗列相关议题（同一轮不要分多次打断）。
2. 每题给 2–5 个**实质不同**的选项，写清代价与收益。
3. 必须给出**明确推荐**及理由，而不是中立罗列。
4. 决议结果写入 `docs/16-open-questions.md`（编号 D 系列，含理由与连带影响）。

哪些**不算**决策、可以直接做：代码风格、文件命名、库版本升级、测试组织、文档排版——凡有明确惯例或可从仓库既有模式推导的，直接执行并说明。

## 2. 工作日志

每轮工作结束必须留日志，路径 `docs/worklog/YYYY-MM-DD-NN.md`。

固定结构：

- 目标
- 完成
- 决议
- 证据
- 遗留
- 下一步

同时更新 `docs/worklog/README.md` 索引表（轮次 / 日期 / 主题 / 文件链接）。

日志要求：事实优先，不写空话；每个结论尽量带文件行号或命令输出；未验证的推断必须标注 `[INFERENCE]`。

## 3. 阶段存档

每个里程碑（M0/M1/M2a/...）完成时：

1. 提交并推送到 `origin/main`，提交信息用英文，格式 `类型: 简述`（`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:`）。
2. 在该阶段工作日志里记录验收结果（对应 `docs/15-final-plan.md` 第 5 节条目）。

## 4. 文档优先级

发生冲突时，以下顺序为权威：

1. `docs/16-open-questions.md`（已决议的产品决策）
2. `docs/15-final-plan.md`（技术与契约定稿）
3. `docs/0X-*.md`（现状基线与阻碍点）
4. `docs/1X-review-*.md`（复审记录，仅供参考）
5. `docs/10-plan-r1.md`（已作废，仅留痕）

## 5. 证据纪律

- 引用源码必须给出 `文件:行号`。
- 未实测的性能/兼容性结论标注 `[INFERENCE]`。
- 交付前若声称「已验证」，必须附上可复现的命令或测试名。

## 6. 写后核验

写入或整体替换源码后，必须在下一步操作前从磁盘独立核验：检查字节数/行数，并确认新增或关键符号存在；有闭合结构时检查括号配对。工具回报写入成功不能代替落盘核验。关键源码变更还须干净重建，避免旧对象文件掩盖真实错误。

## 7. 临时产物

工作过程中产生的临时脚本、样例、调试输出不得提交。清理前先确认其作用与影响；确有保留价值的内容移入 `tests/` 或 `samples/` 并加说明。
